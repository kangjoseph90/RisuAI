# Patch 생성 방식의 신뢰성과 데이터 무결성 보장

사용자께서 제기하신 **"패치 생성 방식(`fast-json-patch`)의 신뢰성"**과 **"클라이언트-서버 간 해시 독립 검증의 필요성"**에 대한 분석 및 답변입니다.

## 1. 패치 생성 방식의 신뢰성 (`fast-json-patch`)

RisuAI가 사용하는 `fast-json-patch` 라이브러리는 **RFC 6902 (JSON Patch)** 표준을 준수하는 구현체입니다.
이 표준은 결정론적(Deterministic)입니다. 즉, 다음 조건이 만족된다면:
1.  **초기 상태(Start State)**가 동일하고,
2.  **패치 연산(Patch Operations)**이 동일하다면,

**결과 상태(End State)**는 반드시 동일함이 보장됩니다.

### 검증 실험 (`tests/patch_determinism.cjs`)
Node.js(서버 환경)와 브라우저 시뮬레이션 환경에서 동일한 데이터에 복잡한 패치(값 변경, 배열 추가, 삭제, 이동 등)를 적용하는 실험을 수행했습니다.
- **결과:** `assert.deepStrictEqual` 통과. 서버와 클라이언트의 데이터 객체 구조가 **완벽하게 일치**함을 확인했습니다.
- **결론:** 패치 적용 로직 자체는 신뢰할 수 있으며, 이로 인한 데이터 불일치는 발생하지 않습니다.

## 2. 왜 독립 검증(Hash Comparison) 대신 서버 해시를 신뢰해야 하는가?

사용자 의견대로 "서버와 클라이언트가 각자 해시를 계산해 비교"하는 것이 가장 이상적인 검증 방법입니다. 그러나 현실적으로는 **"Calculation Drift (계산 편차)"** 문제로 인해 이것이 409 오류 루프의 원인이 됩니다.

### 문제점: Calculation Drift
데이터 내용이 논리적으로 같더라도(`deepEqual` true), 기술적인 표현 방식의 차이로 인해 해시값이 달라질 수 있습니다.
- **예시:** `new String("text")` (객체) vs `"text"` (원시 타입).
- **결과:** 클라이언트 데이터는 정상이지만 해시만 다르게 계산됨 -> 서버에 패치 요청 -> 서버는 "해시 불일치"로 거부(409) -> 무한 반복.

### 해결책: Server Authoritative Sync (서버 권위 동기화)
데이터의 **"Source of Truth (진실의 원천)"**를 서버로 규정합니다.
1.  클라이언트는 패치 적용 후 자신의 해시를 계산합니다.
2.  서버가 보낸 `newHash`와 비교합니다.
3.  **만약 다르다면?**
    - RisuAI는 이를 "데이터 오염"이 아닌 "계산 편차"로 간주합니다 (앞서 패치 로직의 신뢰성이 검증되었으므로).
    - 409 루프를 막기 위해 클라이언트는 서버의 해시를 자신의 기준값(`lastServerHash`)으로 업데이트합니다.
    - **안전장치:** 단, 개발자 콘솔에 `[RisuAI] Hash drift detected...` 경고를 출력하여 잠재적인 문제를 추적할 수 있도록 했습니다.

## 3. 요약

- **패치 로직은 신뢰할 수 있습니다.** (실험으로 입증됨)
- 409 오류의 주원인은 **데이터 불일치가 아니라 해시 계산 방식의 미세한 차이**입니다.
- 따라서 서버의 해시를 받아들이는 것은 데이터 무결성을 해치는 것이 아니라, **무의미한 동기화 오류를 방지하고 서비스 가용성을 보장**하는 합리적인 선택입니다.
